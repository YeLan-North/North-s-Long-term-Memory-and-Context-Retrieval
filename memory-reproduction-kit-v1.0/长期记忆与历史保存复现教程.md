# 长期记忆与历史上下文保存：完整复现教程

版本1.0 · 2026-10-18 · 公开版

本教程从一套实际运行过的配置整理而来。它把原始历史保存、日常日记、分层档案和语义检索连接起来，供其他用户和能调用本机工具的GPT助手复现。

**先理解最终能力：你可以保存指定ChatGPT项目的历史，按每天的消息写细节日记，定期把重要内容整理成长期档案，并在聊天时检索原文。它不复制模型本身，不扩大模型上下文窗口，也不保证任何聊天界面都会自动注入记忆。**

## 1. 功能与流程

### 1.1 数据怎样流动

1. 官方导出用于拿到已有历史；Chrome采集插件用于持续同步明确指定的项目。
2. 对话先保存为原始JSON树，包含消息ID、父子关系、时间、分支和附件引用。
3. 生成离线阅读副本和逐消息JSONL。阅读副本可以精简技术字段，原件保持不动。
4. 每天当地时间13:00，助手读取前一天全部可见消息，生成细节日记及来源索引；可选邮件附件投递。
5. 每周用户手动发起归档：新增原文合并进历史档案，重要内容按层级补充进migration sample。
6. 将分层卡片和原文片段导入本地OpenViking，生成语义索引。
7. 聊天时助手先检索相关卡片与原文，再补读上下文，依据来源继续交流。

这是两条不同的更新链：**采集→日记**可以按时运行；**日记/原文→正式档案→OpenViking**在本方案中由用户手动发起。生成日记不等于检索库已经更新。

### 1.2 各种文件各自负责什么

| 层 | 文件或工具 | 作用 | 可以替代原件吗 |
|---|---|---|---|
| 原始来源 | 官方导出ZIP、采集的raw JSON及本地Git版本 | 保存对话树和元数据，作为核对依据 | 这是来源层，但附件还要另存 |
| 阅读层 | selected-conversations.md、reading.html、messages.jsonl | 方便查找、阅读、按日提取及精确定位 | 不可以 |
| 日记层 | YYYY-MM-DD-Assistant-diary.md | 记录当天事件、细节、感受表达、待办及来源 | 不可以 |
| 分层档案 | migration-sample.md、L0/P/EC/W卡片 | 保留核心设定、偏好、重要事件与世界线 | 不可以 |
| 检索层 | OpenViking的cards、passages和向量索引 | 从当前语义找到相关资料 | 不可以，索引可重建 |
| 当前上下文 | 助手本轮实际读到的资料 | 支持当下回答 | 并非永久存储 |

本教程的L0/P/EC/W是人工设计的档案层级，不要与OpenViking内部的abstract/overview/content层混为一谈。

### 1.3 已验证与尚需验收

参考环境中验证过：本地CPU嵌入与语义检索；插件MCP工具连接；原始文档导入与读回；消息分片；真实项目目录分页与全量首次同步；按日提取；手动按任务指令写日记；把日记作为Gmail附件发送。

仍需在每位用户机器上单独验收：Chrome每30分钟的自动触发；宿主定时任务实际启动、文件权限与完成保存；定时任务是否能使用Gmail连接；宿主是否执行自动记忆钩子。单独执行钩子脚本成功，不代表聊天宿主执行了它。

参考宿主里，自动化管理工具持续报通用错误，但用户在应用界面手动创建了任务；因此教程提供手动建任务方法，不依赖那个接口。不要把应用故障当成你配置文件写错。

主路径针对Apple Silicon Mac，Python3.13、Node.js22+、Git、Chrome，以及支持本机文件和工具调用的助手宿主。其他系统可以改用命令行入口，但Windows/Linux的编译、调度和宿主接入没有在本教程中完整实测。

## 4. 初始化自己的配置

解压后，将文件夹放到一个固定位置，例如 `~/Documents/memory-reproduction-kit-v1.0`。以下命令都从该目录运行。移动目录后，需要重新生成含绝对路径的配置和插件。

```sh
cd ~/Documents/memory-reproduction-kit-v1.0
cp settings.example.json settings.json
```

用任何纯文本编辑器修改 `settings.json`，不需要VS Code：

- `project_ids`：你的项目ID数组。打开项目后检查浏览器地址中的 `g-p-...` 段，只复制这个ID，不要填整条URL或对话ID。若页面暂时打不开，用之前保存的项目链接确认；不要猜。
- `timezone`：IANA时区，例如 `America/Vancouver`。日期边界按时区数据库算，不手写UTC减7。
- `assistant_name`：自己的助手名称，建议用于文件名的简短名称，避免斜线等路径字符。
- `sender_email`、`recipient_email`：需要邮件时填写实际地址；不启用邮件就保留示例，不要粘贴可选邮件段。
- `memory_collection`：自己的集合名，只用英文字母、数字、下划线或短横线，例如 `my-memory-v1`。

```sh
python3 scripts/configure.py
```

它只写本文件夹里的配置，不注册插件、不创建任务、不发邮件。默认 `capture/config.json` 白名单为空，直接启动会拒绝；填好实际项目ID后再配置。不要为了通过检查把白名单改成全账号范围。

生成结果为 `capture/config.json`、`runtime/ov.conf`、`runtime/ovcli.conf`、`runtime/plugin-env.json`、`runtime/instructions/*.md`。后续应复制生成后的指令，而非仍带 `{{占位符}}` 的模板。

## 5. 安装并验收持续采集

### 5.1 启动接收端

采集端使用Python标准库，不需要安装OpenViking也能运行。需要Python和Git。

```sh
python3 capture/bin/chatgpt-sync serve
```

Mac也可双击 `capture/Start-Capture.command`。若系统没有执行权限，运行 `chmod +x capture/Start-Capture.command`。终端保持打开，Ctrl+C停止。默认仅监听 `127.0.0.1:8765`，不要对外暴露。端口占用时先确认已有接收器，不能随意结束其他进程。

### 5.2 安装Chrome扩展

1. 在Chrome登录自己的ChatGPT账号。
2. 打开 `chrome://extensions`，打开开发者模式。
3. 选择“加载已解压的扩展程序”，选本包的 `capture/extension` 文件夹。
4. 固定扩展图标，打开弹窗，点击“立即同步”。
5. 核对项目数、列出/下载/保存数量、完整状态及失败清单。首次同步可能需要几分钟。

扩展沿用上游公开公钥和ID，接收端的Origin检查与之匹配；不要同时加载上游原版。公钥不是秘密，不应在去个人化时盲目删除，否则扩展ID会变化。若自定义公钥，必须同步修改接收端 `EXTENSION_ORIGIN` 并重新验收。

### 5.3 它采集的是什么时间范围

首次采集整个白名单项目中接口能列出的历史对话，没有“只采前一天”的限制。后续每次重新枚举项目目录，对新增或更新时间变化的对话下载完整正文，未变化的跳过。

后台使用非公开接口：浏览器内 `/api/auth/session` 获取当轮凭据；`/backend-api/gizmos/<项目ID>/conversations?cursor=...` 枚举项目；`/backend-api/conversation/<对话ID>` 读取树。凭据只存在当轮后台变量中，不发给本地接收器、不写入报告或配置。不需要手动复制Cookie或令牌。登录过期、403、验证码或返回结构变化时停止相应采集并记录失败。

扩展已设30分钟alarm，安装和浏览器启动时建立定时检查。它不是安装后立即完成首次同步；刚手动同步后会受间隔限制。Chrome、接收器需要运行，电脑需要唤醒。后台请求不要求一直打开聊天页，但也不能保证整个浏览器卡死时仍能采集。页面 `RESULT_CODE_HUNG` 时后台请求在参考环境中仍完成过采集，不代表所有崩溃情况都能绕过。

### 5.4 保存位置与完整性

- `capture/data/raw/<conversation_id>.json`：原始树，包含技术节点和附件引用。
- `capture/data/index.json`：范围、更新时间及格式版本。
- `capture/data/markdown/`：逐条消息阅读副本。
- `capture/data/.git`：每次同步的本地版本；没有自动push。
- `capture/state/runs/`：每轮结果。
- `capture/state/last-sync.json`：最近结果。

接口格式异常、时间无效、分页游标循环、项目归属不符、正文陈旧、落盘拒绝等均记录为失败。只有完整成功才更新完整成功状态。这里的“完整”只针对实际观测到的目录，不保证包含已经删除、不可见、无权限或接口根本未列出的聊天。

**附件只保留引用，不下载图片、音频、PDF、生成文件本体。**重要附件应另存，与来源消息关联。不要把这套采集称为含全部附件的完整账号备份。

### 5.5 采集验收

先手动同步通过，再等待30～60分钟检查最近完成时间和新报告是否变化。新增一条无隐私测试消息，检查它是否进入raw；不要只看扩展图标。若自动检查不发生，在扩展详情中检查service worker和alarm错误，保留失败报告，不把手动成功直接判成自动成功。

## 6. 官方历史导出、快速定位和阅读副本

如果已有导出ZIP，原件另存。按官方帮助说明申请导出，解压后寻找实际包含对话数组和 `mapping` 树的JSON。文件可能是一份或多份；本教程不假定每个账号都叫 `conversations-018.json`。编号只是拆分名，不是日期，不保证重要记忆一定在末尾。

用编辑器跨文件搜索一个有辨识度的旧称呼、专名或原话，定位相关文件；没有匹配时换同义词或更短片段。也可使用：

```sh
rg -l '你的检索词' /path/to/unpacked-export --glob '*.json'
```

不安装rg也可以在Subtext等编辑器里搜索。JSON中的Unicode转义可能让中文搜索失效，此时先转换为解码的阅读副本。

```sh
python3 scripts/export_reader.py /path/to/conversations.json --output private/history-reading --timezone America/Vancouver
```

多份导出可以依次列在命令中。输出 `reading.html` 可离线浏览和全文搜索；`selected-conversations.md` 方便助手读取；`selected-messages.jsonl` 保存来源与原始message对象；`reading-manifest.json` 记录数量、缺失时间和源文件SHA256。

HTML本身不上传数据。要筛选整段对话，先从HTML找到对话ID，把需要保留的ID每行一个放进 `private/selected-ids.txt`，再运行：

```sh
python3 scripts/export_reader.py /path/to/conversations.json --ids-file private/selected-ids.txt --output private/selected-history
```

转换按树的父子关系顺序遍历，每个节点只出现一次；用 `current_node` 向父链判断当前路径，其他节点标 `alternative`，保留parent和source_order。当前路径不等于现实或故事主线。工具、分析及隐藏上下文不进入阅读副本，仍应保存在原始JSON。时间缺失的可见消息被列入缺失清单并返回退出码2，不默默归到某天。

此公开转换器与最初为特定导出编写的专用页面不同，采用通用JSON结构、ID筛选和JSONL来源记录，不依赖原用户的文件行号或档案索引。遇到相同对话不同快照时拒绝自动覆盖，需要先选择保留哪个版本。

## 7. 按日提取、日记、调度与邮件

### 7.1 先验收按日原文

```sh
python3 capture/bin/chatgpt-sync day --date 2026-10-17 --output runtime/daily
```

把日期换成要提取的一天。输出 `.jsonl`、`.md`、`.manifest.json` 三份。日期按配置时区的当地午夜划分，跨日对话只提取当天消息，不以整段对话更新时间判断。

状态 `complete_for_observed_inventory` 表示针对已观测目录完成；`partial` 或退出码2表示有缺口，仍保存已取得内容。快照必须晚于目标日结束；当前未结束的一天不能冒充完整日记。仅修改标题或更新时间而没有当天消息的对话不计入当天。

### 7.2 日记为什么不能只写摘要

全文原文继续保留；日记需要保留重要事件的因果、具体对话、用户反馈和未决事项。来源索引让摘要可以回到原话，降低压缩后断章取义的风险。

使用 `runtime/instructions/daily-task.md`。先手动测试一个已结束的日期，核对：导出消息数和日记覆盖表一致；真实/虚构分开；没有把未执行的建议写成已完成；没有猜图像或音频；保存后的文件可打开。

### 7.3 创建每日任务

在支持本地执行的助手应用里手动创建：名称“整理昨日对话并生成日记”；每天13:00；选择自己的IANA时区；执行方式本地；正文复制生成后的日记指令中实际执行部分。设置正确的文件访问范围，模型选择自己账号可用、能充分阅读当天记录的模型。

不要把本地路径放进普通云端提醒，就期待它访问你的Mac。无法本地执行时，先采用每日手动上传导出文件。应用里只有“提醒”而没有工具执行能力，也不能完成日记流水线。

生成配置不等于注册了定时任务，本包不直接写宿主内部automation.toml。任务创建后，核对启用状态、时区、下次运行、执行环境和指令。点击“立即运行”测试，再等一次真实定时触发；电脑唤醒与宿主运行要求以实际应用行为为准，本方案建议保持运行。休眠错过的任务是否补跑没有验证，不能作保证。

### 7.4 邮件附件投递（可选）

连接Gmail后，先让助手只读当前账号资料，核对确为填写的发件地址。收件人使用用户明确提供的完整地址，不猜人名。用户明确启用后，将生成指令的“可选邮件投递段”加入任务正文。

邮件标题为 `Assistant的日记｜YYYY-MM-DD`，其中日期是日记日期，不是发送日期。附件是真实 `.md` 文件，不只是链接，也不默认发送原始聊天压缩包。正文可以简短署名。发送前查同日已发送记录；不确定结果先核查，避免重复。

在支持Gmail MIME发送的工具中，以 `multipart/mixed` 组合一个正文part和一个带filename、`content_disposition=attachment` 的 `text/markdown; charset=UTF-8` part。内容应来自已保存日记，保持完整，不只取预览。其他宿主可以使用自己的等效邮件工具；本包不含邮箱密码、OAuth令牌、SMTP账号或自动发信脚本。

一次聊天里发信成功，只证明当次连接可用。定时运行能否获得该连接和发送权限，必须实际测试。如果只有Library而没有Gmail工具，则保留文件并报告，不要声称已发出。

## 8. 安装OpenViking与本地嵌入

### 8.1 创建隔离环境

从工具包根目录执行，确保 `python3.13` 指向自己安装的Python：

```sh
python3.13 -m venv .venv
./.venv/bin/python -m pip install --upgrade pip
./.venv/bin/python -m pip install 'openviking==0.5.0'
```

不要复制别人的 `.venv` 或本机wheel来替代安装。它们包含平台路径和编译差异。

### 8.2 CPU构建与Metal问题

参考机曾遇到预编译包校验失败，随后源码构建遇到C++头文件路径和Metal上下文问题。仅传 `-DGGML_METAL=OFF` 还不够：该版本Apple的CMake段会强制设回ON。因此复现脚本同时修改那一行并设置构建选项。

```sh
python3.13 scripts/build_cpu_llama.py
```

脚本从PyPI0.3.36元数据选择源包，用发布SHA256校验，安全解包；将强制Metal ON改为OFF；在Mac用 `xcrun --show-sdk-path` 取得SDK并提供C++头文件路径；构建wheel并安装进本包 `.venv`。源码、构建回执和wheel在 `vendor/llama-cpu-build`。无需购买API；编译可能需要几分钟。脚本使用Python3.12+的安全解包接口，参考使用3.13。

若没有出现Metal问题，也可按上游安装合适wheel后做实际嵌入测试；本教程的确定参考路径是CPU构建。不要把通用CPU方案说成所有硬件上的最佳性能方案。

### 8.3 下载模型

OpenViking本地provider首次使用会按内置地址下载；也可手动将模型放到 `runtime/models/bge-small-zh-v1.5-f16.gguf`：

```sh
curl -L --fail 'https://huggingface.co/CompendiumLabs/bge-small-zh-v1.5-gguf/resolve/main/bge-small-zh-v1.5-f16.gguf?download=true' -o runtime/models/bge-small-zh-v1.5-f16.gguf
shasum -a 256 runtime/models/bge-small-zh-v1.5-f16.gguf
```

核对 `dependency-sources.json` 的参考哈希与大小。模型URL指向main，未来可能变化；不符时先审查来源，不静默接受。该模型为中文、512维；英文为主或其他领域需要另评估召回质量。换模型或维度后要重建索引，不能混用旧向量。

### 8.4 启动与检查

```sh
./.venv/bin/openviking-server --config runtime/ov.conf
```

或使用 `scripts/start-memory.command`。保持此终端打开。另一终端运行：

```sh
python3 scripts/memory_cli.py health
```

配置采用本地storage、127.0.0.1:1933、本地GGUF、关闭自动生成L0/L1；没有生成模型或密钥。它足以做 `vectors_only` 导入、find和read，不提供自动摘要、记忆提取或模型查询改写。某个依赖包名叫openai，不等于已经调用收费API。

仅供单机个人使用，未配置远程认证或多用户隔离；不要把无认证服务发布到局域网或公网。数据目录 `runtime/data` 和模型目录都含本机绝对路径，移动后要重新configure。启动脚本不会自动配置开机启动。

## 9. 准备、安装并信任检索插件

### 9.1 准备仅召回版本

```sh
python3 scripts/prepare_plugin.py
```

脚本下载固定官方Git提交，复制插件并显式放入共享库；生成本机Node路径、连接环境、marketplace，以及仅含 `SessionStart` 和 `UserPromptSubmit` 的hooks。下载失败可以自己按固定源码地址取得完整仓库并检出固定提交，再用 `--source /path/to/OpenViking`。源码路径必须是可验证HEAD的Git仓库；普通ZIP解压目录不满足这个校验，需要先用Git获取固定提交。

输出在 `runtime/plugin-marketplace`。脚本只准备文件，不注册或信任。若目标已存在，会拒绝覆盖；先备份旧目录再重建。下载后的第三方插件与共享库都保留上游许可；本包没有另带一份私有改写的整套官方插件。

### 9.2 注册、加载、信任

先在宿主提供的终端或自己的终端确认 `codex --version` 和插件子命令是否存在。如果CLI没有加入PATH，查自己应用正式提供的CLI位置；不要照抄原用户安装路径。不同版本命令可能叫add或install，先看 `codex plugin --help`。

```sh
codex plugin marketplace add /absolute/path/to/memory-reproduction-kit-v1.0/runtime/plugin-marketplace
codex plugin add openviking-memory@local-memory-kit
```

然后在应用插件列表检查、启用并重新加载；审核两个钩子后通过应用界面信任。配置中若有hooks功能开关，以对应版本官方说明为准，不要往已有配置里重复追加冲突的 `[features]` 段。信任只表示允许执行，不表示宿主一定会触发。

此版本禁用聊天自动捕获、Stop提取、PreCompact捕获、生成模型压缩和查询扩展，来源展示关闭。保留的两个钩子是用于验证的候选路径；本方案持续采集由Chrome组件负责，不靠这些钩子。

生成的环境配置还包括：`OPENVIKING_CLI_CONFIG_FILE`和`OPENVIKING_CONFIG_FILE`指定连接与服务配置；`OPENVIKING_STATE_DIR`和`OPENVIKING_CODEX_STATE_DIR`保存钩子状态；`OPENVIKING_CREDENTIAL_SOURCE=cli`使用CLI连接配置；`OPENVIKING_AUTO_CAPTURE=0`关闭捕获；`OPENVIKING_USAGE_VIEW=off`关闭来源展示；`OPENVIKING_RECALL_COMPRESS=off`、`OPENVIKING_RECALL_QUERY_EXPANSION=off`及`OPENVIKING_RECALL_COMPRESS_DETECT_ON_STARTUP=0`关闭生成模型依赖。配置中的autoRecall=true仍不代表宿主会执行钩子。

若要在支持钩子的宿主测试会话开始档案加载，官方脚本读取的是 `viking://user/default/memories/profile.md`，不是资源集合中的cards/L0.md。可把自己的简短核心档案另写入该URI，再检查真实SessionStart记录；两份内容更新需要保持一致。未验证宿主时，继续明确读取cards/L0.md即可，不必假装已注入。

### 9.3 验收工具和钩子要分开

1. 工具：新聊天检查是否能发现OpenViking的find/read等工具，查询一条合成测试资料并读取原文。
2. 钩子：检查宿主实际运行记录或有证据的额外上下文；用不在当前聊天里的合成资料测试。直接执行脚本返回additionalContext，只证明脚本和服务能连接。
3. 若工具正常、钩子没有执行证据，使用明确读取指令，继续完成工作。不把“安装成功”写成“每次发言已经自动记忆”。

“只有助手可见”也有界面边界：工具结果通常进入助手上下文，但宿主可能显示活动记录；关闭来源展示不保证绝对隐藏，也不是独立的秘密人格注入通道。

## 10. 整理档案、分片和导入

### 10.1 分层档案设计

首次可将 `runtime/instructions/initial-import.md` 交给能完整读取历史的助手执行；这一步是有来源的人工/助手整理，不是已配置的自动提取模型。

从 `templates/migration-sample.md` 开始，用自己的历史填写：L0保持短，放核心与读取规则；P记录明确偏好与约定；EC记录重要事件的完整来龙去脉；W记录彼此独立的虚构世界线；另记冲突、缺失和来源。

不要只存性格设定，否则检索只能找到“是谁”，找不到“为什么这样”。重要事件卡需要起因、过程、结果、用户反馈和来源消息。也不要把所有消息塞进L0；核心档案负责引路，细节从原文找回。

把各卡拆成Markdown文件放进 `runtime/cards`，其中 `L0.md` 必须由用户填写，不能直接复制合成示例。长卡应按语义拆小；使用512上下文的嵌入模型时，长段会有截断风险。原文另保留整份，只把小片段作为精细检索入口。

### 10.2 按消息生成有来源的原文片段

使用第6节的 `selected-messages.jsonl`，或第7节按日导出的JSONL：

```sh
./.venv/bin/python scripts/make_passages.py private/selected-history/selected-messages.jsonl --output runtime/passages-v1 --model runtime/models/bge-small-zh-v1.5-f16.gguf
```

每个分片包含对话ID、消息/节点ID、父节点、角色、时间、分支、原始顺序、片段号和正文偏移。默认连同这些元数据不超过480个真实模型token，为512上下文留余量。分片按渲染后的可读正文无损拼接，清单记录哈希；原始message对象仍在JSONL，因此保留附件引用和技术信息的核对依据。

输出必须是空目录，避免旧片段残留。分片名按稳定节点身份哈希生成，不靠用户名或消息正文。长消息可以分多片，但检索命中后必须补读其他片和相邻消息。仅取top1片段不足以恢复上下文。

这比对整篇长历史直接做一个向量更可靠。关键词、精确名字或漏召回时，补用本地 `rg` 搜索原文。不要把语义模型当作唯一入口。

导入cards前运行实际token检查；超长卡拆为多张关联卡，长原文继续保留：

```sh
./.venv/bin/python scripts/check_token_budget.py runtime/cards --model runtime/models/bge-small-zh-v1.5-f16.gguf
```

### 10.3 导入并逐项读回

以下 `my-memory-v1` 换成自己的集合名，保持与生成的聊天读取指令一致。

```sh
python3 scripts/memory_cli.py put-dir runtime/cards --uri viking://user/default/resources/my-memory-v1/cards --receipt runtime/cards-receipt.json
python3 scripts/memory_cli.py put-dir runtime/passages-v1 --uri viking://user/default/resources/my-memory-v1/passages --receipt runtime/passages-receipt.json
python3 scripts/memory_cli.py put-file private/selected-history/selected-conversations.md --uri viking://user/default/resources/my-memory-v1/source/selected-conversations.md --receipt runtime/source-receipt.json
```

工具使用OpenViking本地REST content/write、`processing_mode=vectors_only`、wait=true，逐项写入并raw读回比较，保存失败清单。原文整份通过直接content/write保持正文，不经过Markdown解析拆分；这是公开工具对最初资源导入路径的简化替代。整份原文的长文本向量不能覆盖所有细节，精细检索依赖passages。不要把原文读回一致等同于语义检索质量合格。

原始JSON/ZIP还应在本地另存，源文件大小、SHA256和各版本记录也应保存。读回校验比较的是UTF-8文本；不要因此声称原始ZIP或二进制附件已逐字节备份。

### 10.4 检索测试

```sh
python3 scripts/memory_cli.py find '某次重要事件为什么发生？' --uri viking://user/default/resources/my-memory-v1/cards
python3 scripts/memory_cli.py find '那天具体怎样回答的？' --uri viking://user/default/resources/my-memory-v1/passages
python3 scripts/memory_cli.py read 'viking://user/default/resources/my-memory-v1/cards/L0.md'
```

至少测：改写后的核心事实；普通事件细节；近期尾部消息；另一分支；一个本来就不存在的问题。核查命中内容和来源，不能只看相似度或返回数量。合成资料应放到独立测试集合，验收后不要让正式读取指令搜索它。

## 11. 每次聊天如何使用

把 `runtime/instructions/chat-recall.md` 放进项目说明或每次新聊天的开头，确认集合URI正确。先读L0，再根据话题find卡片和passages；检索到后用read读取，不只凭工具摘要。需要前因后果时，按JSONL中的parent、source_order、分片manifest补读上下文。

连接和工具名因宿主而异，助手应先发现可用工具，不照抄本教程某个会话特有的内部工具名。没有OpenViking连接时可手动上传L0、事件卡与原文片段，仍能获得部分连续性，但不能声称正在查询本地库。

明确指令能提高主动检索的一致性，不保证每轮一定执行；检索不准时先查看原文与范围，不马上重写人格档案。自动钩子未验证时，用户可以直接说“查一下记忆库里关于X的原话和上下文”。

## 12. 周度更新与上下文压缩

使用 `runtime/instructions/weekly-merge.md`，明确本次日期范围与待更新文件。按conversation_id+node_id合并，保留修改版本与分支，不用相似文本去重。日记用于发现候选记忆，原文负责验证。只有阅读Markdown且无稳定ID时，不能可靠地自动合并，应先恢复来源索引或人工核对。

推荐以新集合名导入每次正式版本，验收通过后切换读取指令；不要用更新目录覆盖后留下已删除旧片段。旧集合和原档保留便于回退。当前工具不自动完成周归档，不自动清除旧集合。

本方案的压缩方式是“短核心+事件卡+日记+可回查原文”，不是已接入宿主的PreCompact自动模块。参考配置关闭OpenViking生成模型压缩和查询改写。若将来启用，需另外配置生成模型、计费或本地推理能力，并验收提取遗漏、错误归因、矛盾处理和来源可追溯性。

上下文压缩后，助手应重新读L0和当前任务相关事件卡，再读取原文；工具包本身不能强制宿主在压缩完成时执行重载。不能承诺永久记住，能做到的是把可验证的资料放在可重新读取的位置。

## 13. 故障定位

| 现象 | 检查与解决 |
|---|---|
| 接收器启动就报白名单错误 | 填实际project_ids并运行configure；确认未加载空配置 |
| 扩展无法连接localhost | 接收器、端口8765、host权限、扩展ID与Origin匹配 |
| 403或返回结构不认识 | 重新确认登录与项目权限；保存失败报告；接口变化需更新代码 |
| 手动同步成功但没有自动同步 | 等一个完整周期，检查Chrome运行、电脑唤醒、alarm/service worker日志 |
| 按日结果为partial | 读manifest中的具体错误；先同步到目标日结束之后；处理无时间消息 |
| C++头文件找不到 | 确认开发工具，SDK路径与架构；按CPU构建脚本使用xcrun |
| Metal上下文失败 | 关闭强制Metal的源码开关后重建；只设环境变量可能被覆盖 |
| OV健康正常但find为空 | 检查导入回执、URI范围、真实嵌入、片段长度和模型维度 |
| 插件安装了却没有记忆 | 分别验收MCP工具、插件启用、钩子信任及宿主触发；采用明确指令 |
| 定时任务管理接口报-32000 | 不知道具体根因时不要宣称重启必好；用应用UI手动创建并核验配置 |
| 定时任务找不到文件 | 本地执行、绝对路径、工作目录、文件权限、安装目录是否移动 |
| 日记写出但邮件没到 | 核对连接账号、真实附件、发送结果及已发送记录；定时权限单独验收 |
| 回忆只有设定，没有来龙去脉 | 补EC事件卡和原文passages，读取前后消息，不只扩大L0 |

## 14. 日常运行、备份、停止与撤销

日常需要：Chrome采集运行、本地接收器运行；需要检索时OpenViking服务运行；日记任务时间到时本地宿主可执行。三者独立，不要以某一个窗口在线判断整个系统正常。

备份自己的官方导出、附件、raw与本地Git、state报告、日记、档案、来源JSONL和分片清单。OpenViking数据最好停止服务后做一致性副本，或从原文重建；不要边写边简单复制数据库就宣称备份一致。模型可重新下载。

停止两个终端按Ctrl+C；暂停任务用应用UI；停用采集在Chrome扩展页禁用。移除插件可按当前CLI帮助执行 `codex plugin remove openviking-memory@local-memory-kit` 和 `codex plugin marketplace remove local-memory-kit`。不执行任何删除原始数据的命令，除非用户另行决定。

公开分享时重新从干净包开始；不要分享使用后的runtime、settings.json、capture/data/state、Git历史、日志、邮箱令牌和完整用户档案。共享Git仓库即使删除了当前文件，也可能在历史里保留旧内容。不要直接将私人安装目录上传到GitHub。

## 16. 给接手助手的执行摘要

先读本教程、NOTICE、settings.example和dependency-sources；只在用户明确的目录内操作。帮助用户填写自己的设置，不索取或复制浏览器令牌。先跑采集和离线导出的最小闭环，再做日记、调度、邮件，最后接检索。

使用包内修改后的采集代码，外部依赖按固定来源下载；不要复制参考机的个人配置或虚拟环境。保留原件，把阅读层、摘要层和检索层当成可重建派生物。遇到工具不可用或宿主不支持，报告具体阻塞并采用已验证的手动流程，不把未执行步骤写成完成。每一步都用实际消息、来源ID和执行回执验收。
